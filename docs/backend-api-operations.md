# Team Knowledge — API для бэкенда: операции

Что фронтенд отправляет на сервер и что ждёт в ответ — по каждой операции отдельно.
Каждая операция описана полностью: схемы повторяются там, где нужны.

## Общее

- **Базовый URL** задаётся на фронтенде в `VITE_API_URL`; все пути ниже указаны относительно него.
- **Формат** — JSON в UTF-8.
- **Даты** — строки ISO-8601 в UTC с миллисекундами: `"2026-10-06T12:04:31.123Z"`.
- **Id проектов, зарисовок, досок и документов** назначает сервер при создании, рекомендуется UUID v4. Id элементов на доске назначает клиент.
- **Иерархия:** проект → зарисовки (`projectId`) → доски и документы (`spaceId`). Родитель не хранит список детей, ребёнок ссылается на родителя по id.
- **Оптимистичная блокировка.** У каждой сущности есть `version`. При сохранении (`update_*`) клиент присылает прочитанную версию в заголовке `If-Match` и в теле. Сервер сохраняет, только если она совпадает с текущей, и отвечает сущностью с `version + 1`. Иначе — `409` и никаких изменений.
- **Авторизация.** Все операции, кроме `/auth/*`, требуют заголовок `Authorization: Bearer <accessToken>` (токен из `verify_login_code`); в таблицах заголовков ниже он не повторяется. Нет токена, он просрочен или отозван → `401 UNAUTHORIZED`, фронтенд разлогинивает пользователя.
- **Порядок операций** ниже: вход, проекты, зарисовки, доски, документы. В конце — сводная таблица.

## Вход и профиль

Вход и регистрация — одно и то же: email → код из письма → сессия. Если аккаунта не было, он создаётся
при первом `verify_login_code`, с `name: null` — тогда фронтенд просит имя и компанию (`update_me`).

`User`: `id` (string), `email` (string, в нижнем регистре), `name` (string | null — профиль не заполнен),
`company` (string | null), `createdAt` (ISO-8601 UTC).

### request_login_code

**Отправить код на почту.** Вызывает: `RequestLoginCode` — шаг 1 экрана входа и «Отправить код ещё раз».

```http
POST /auth/code HTTP/1.1
Content-Type: application/json; charset=utf-8

{ "email": "ann@example.com" }
```

**Успешный ответ:** `204 No Content`. Сервер генерирует одноразовый 6-значный код (рекомендуется: живёт
~10 минут, до 5 попыток) и отправляет письмо; прежний код этого email становится недействительным.

| Статус | `code` | Когда | Что делает фронтенд |
|---|---|---|---|
| `422` | `INVALID_EMAIL` | адрес некорректен | «Проверьте адрес почты» |
| `429` | — | слишком частые запросы | «хранилище недоступно», можно повторить |

### verify_login_code

**Войти по коду (и зарегистрироваться при первом входе).** Вызывает: `VerifyLoginCode` — шаг 2, отправляется
автоматически после 6-й цифры.

```http
POST /auth/verify HTTP/1.1
Content-Type: application/json; charset=utf-8

{ "email": "ann@example.com", "code": "123456" }
```

**Успешный ответ:** `200 OK` — сессия.

```json
{
  "accessToken": "eyJhbGciOi…",
  "expiresAt": "2026-11-07T12:00:00.000Z",
  "user": { "id": "7c0e…", "email": "ann@example.com", "name": null, "company": null, "createdAt": "2026-10-08T12:00:00.000Z" }
}
```

`accessToken` — JWT, клиент его не разбирает. `expiresAt` — когда клиент сам перестанет считать сессию
действующей. Повторный вход тем же email возвращает того же пользователя.

| Статус | `code` | Когда | Что делает фронтенд |
|---|---|---|---|
| `422` | `INVALID_EMAIL` | адрес некорректен | «Проверьте адрес почты» |
| `422` | `INVALID_CODE`, `reason: "format"` | не 6 цифр | «Код — это 6 цифр» |
| `422` | `INVALID_CODE`, `reason: "wrong"` | не тот код | «Неверный код» |
| `422` | `INVALID_CODE`, `reason: "expired"` | код истёк или исчерпаны попытки | «Код устарел — запросите новый» |

### update_me

**Заполнить профиль после регистрации.** Вызывает: `CompleteProfile` — шаг 3 экрана входа (только когда `user.name === null`).

```http
PUT /me HTTP/1.1
Authorization: Bearer eyJhbGciOi…
Content-Type: application/json; charset=utf-8

{ "name": "Анна", "company": "Acme" }
```

`name` — обязательно, 1–100 символов после `trim`; `company` — `null` или до 100 символов.

**Успешный ответ:** `200 OK` — `User` целиком. Клиент кладёт его в сохранённую сессию.

| Статус | `code` | Когда | Что делает фронтенд |
|---|---|---|---|
| `401` | `UNAUTHORIZED` | нет/просрочен токен | выход, экран входа |
| `422` | `INVALID_NAME` | имя пустое или длинное, компания длинная | «Укажите имя» |

## Проекты

### get_projects

**Список проектов.** Вызывает: `ListProjects` — главная страница.

```http
GET /projects?limit=100 HTTP/1.1
Accept: application/json
```

Следующие страницы: `GET /projects?limit=100&cursor=<nextCursor>`.

**Параметры запроса (query)**

| Параметр | Тип | Обязателен | По умолчанию | Описание |
|---|---|---|---|---|
| `limit` | integer 1…200 | нет | `100` | сколько элементов на страницу; больше 200 — сервер урезает до 200 |
| `cursor` | string | нет | — (первая страница) | значение `nextCursor` из предыдущего ответа. Строка непрозрачная: клиент её не разбирает, только передаёт обратно |

**Заголовки запроса**

| Заголовок | Значение | Обязателен | Описание |
|---|---|---|---|
| `Accept` | `application/json` | да | клиент ждёт JSON |

**Payload:** нет.

**Успешный ответ:** `200 OK`.

**Заголовки ответа**

| Заголовок | Значение | Обязателен | Описание |
|---|---|---|---|
| `Content-Type` | `application/json; charset=utf-8` | да | тело ответа — JSON |

**Схема ответа — страница списка**

| Поле | Тип | Описание |
|---|---|---|
| `items` | array of `Project` | элементы этой страницы (может быть пустым) |
| `nextCursor` | string \| null | курсор следующей страницы; `null` — это последняя страница |
| `total` | integer, необязательно | сколько всего элементов в коллекции на момент запроса; клиенту пока не нужно |

**Схема `Project` (элемент `items`)**

| Поле | Тип | Описание |
|---|---|---|
| `schemaVersion` | integer | версия формата тела; сейчас всегда `1`. Клиент отклонит ответ, где число больше известного ему |
| `id` | string | id сущности; назначает сервер при создании (рекомендуется UUID v4) |
| `name` | string | название проекта; после обрезки пробелов по краям — от 1 до 100 символов |
| `version` | integer ≥ 1 | версия для оптимистичной блокировки: новая сущность — `1`, каждое успешное сохранение — `+1` |
| `createdAt` | string, ISO-8601 UTC | когда создана, например `"2026-10-06T12:04:31.123Z"`; ставит сервер, не меняется |
| `updatedAt` | string, ISO-8601 UTC | когда последний раз сохранена; ставит сервер при каждом сохранении |

**Пример ответа**

```json
{
  "items": [
    {
      "schemaVersion": 1,
      "id": "5b9d54d2-f918-41b5-beff-efc546bf5f0b",
      "name": "Интернет-магазин",
      "version": 3,
      "createdAt": "2026-10-01T09:00:00.000Z",
      "updatedAt": "2026-10-06T12:04:31.123Z"
    }
  ],
  "nextCursor": "eyJjIjoiMjAyNi0xMC0wMVQwOTowMDowMC4wMDBaIiwiaSI6IjViOWQ1NGQyLWY5MTgtNDFiNS1iZWZmLWVmYzU0NmJmNWYwYiJ9",
  "total": 12
}
```

На последней странице `"nextCursor": null`. Если проектов нет — `{ "items": [], "nextCursor": null }`.

**Поведение**

- Клиент запрашивает страницы, пока `nextCursor` не станет `null`, затем склеивает `items` и убирает дубли по `id`.
- Порядок выдачи: `createdAt` по возрастанию, при равных — `id` по возрастанию. Эти поля у записи не меняются, поэтому при листании ничего не пропадает и не задваивается, а новые записи попадают в конец. Для показа клиент сортирует сам, по `updatedAt`.
- Пока данных мало, можно всегда отдавать всё одной страницей с `"nextCursor": null`.

**Как устроен курсор**

Курсор — закладка «последним на прошлой странице был вот этот элемент». Клиент его не разбирает и не собирает: берёт `nextCursor` из ответа и возвращает как есть в параметре `cursor`, URL-кодированным.

Рекомендуемый формат — JSON с двумя полями последнего элемента страницы, закодированный в **base64url без `=` на конце** (RFC 4648, §5). Такую строку можно вставить в URL без экранирования.

| Поле | Значение |
|---|---|
| `c` | `createdAt` последнего элемента страницы, строка ISO-8601 — **с той же точностью, с какой время хранится в базе** |
| `i` | `id` последнего элемента страницы |

Пример: курсор `eyJjIjoiMjAyNi0xMC0wMVQwOTowMDowMC4wMDBaIiwiaSI6IjViOWQ1NGQyLWY5MTgtNDFiNS1iZWZmLWVmYzU0NmJmNWYwYiJ9` раскодируется в

```json
{"c":"2026-10-01T09:00:00.000Z","i":"5b9d54d2-f918-41b5-beff-efc546bf5f0b"}
```

Как сервер обрабатывает запрос:

1. `limit`: нет — `100`; больше `200` — `200`; меньше `1` или не число — `400 INVALID_DATA`.
2. `cursor`: нет — выдача с начала. Есть — раскодировать base64url, разобрать JSON, проверить, что `c` — дата, а `i` — строка. Не получилось — `400 INVALID_CURSOR`.
3. Выбрать на одну запись больше, чем `limit`. Лишняя запись нужна, только чтобы узнать, есть ли продолжение:

   ```sql
   SELECT * FROM projects
   WHERE (created_at, id) > (:c, :i)   -- только если пришёл cursor
   ORDER BY created_at, id
   LIMIT :limit + 1
   ```

   Если база не умеет сравнивать пары, то же условие записывается так: `created_at > :c OR (created_at = :c AND id > :i)`. Нужен индекс по `(created_at, id)`.
4. Пришло больше `limit` записей — лишнюю отбросить, а `nextCursor` собрать из **последней оставшейся** записи. Пришло `limit` или меньше — `nextCursor: null`.
5. `total`, если отдаёте: `SELECT count(*) FROM projects`.

Тонкости:
- Курсор хранит значения, а не ссылку на запись. Если эту запись потом удалили, курсор продолжает работать: условие «после такого-то времени и id» по-прежнему однозначно.
- Точность времени в курсоре должна совпадать с точностью в базе. Если база хранит микросекунды, а в курсор попадут миллисекунды, записи на границе страниц задвоятся или потеряются. Либо кладите в `c` время с полной точностью, либо округляйте `created_at` до миллисекунд уже при записи.
- Формат курсора — внутреннее дело сервера, его можно поменять в любой момент: клиент на содержимое не смотрит. Подписывать или шифровать курсор не обязательно. Подделанный курсор только сдвинет выдачу, а мусор сервер отклонит с `400 INVALID_CURSOR`.

**Ошибки**

Тело ошибки — объект `error`: `code` (код из таблицы), `message` (описание для логов), а для `404` ещё `entity` и `id` — какой сущности не нашлось. Пример:

```json
{ "error": { "code": "INVALID_CURSOR", "message": "cursor cannot be parsed" } }
```

Заголовок ответа с ошибкой — `Content-Type: application/json; charset=utf-8`.

| Статус | `code` | Когда | Что делает фронтенд |
|---|---|---|---|
| `400` | `INVALID_CURSOR` | `cursor` не удаётся разобрать (не base64url, не JSON, нет полей `c` и `i`) | один раз начинает листание заново с первой страницы |
| `5xx`, сеть, таймаут | — | сбой сервера | показывает «хранилище недоступно» и предлагает повторить |

### update_project

**Сохранить проект.** Вызывает: `RenameProject` — переименование на главной.

```http
PUT /projects/{projectId} HTTP/1.1
Accept: application/json
Content-Type: application/json; charset=utf-8
If-Match: "3"
```

**Заголовки запроса**

| Заголовок | Значение | Обязателен | Описание |
|---|---|---|---|
| `Accept` | `application/json` | да | клиент ждёт JSON |
| `Content-Type` | `application/json; charset=utf-8` | да | тело запроса — JSON в UTF-8 |
| `If-Match` | `"3"` (в кавычках) | да | `version`, которую клиент прочитал; совпадает с полем `version` в payload |

**Схема payload — `Project` целиком**

| Поле | Тип | Описание |
|---|---|---|
| `schemaVersion` | integer | версия формата тела; сейчас всегда `1`. Клиент отклонит ответ, где число больше известного ему |
| `id` | string | id сущности; назначает сервер при создании (рекомендуется UUID v4) |
| `name` | string | название проекта; после обрезки пробелов по краям — от 1 до 100 символов |

**Схема ответа — `Project`**

| Поле | Тип | Описание |
|---|---|---|
| `schemaVersion` | integer | версия формата тела; сейчас всегда `1`. Клиент отклонит ответ, где число больше известного ему |
| `id` | string | id сущности; назначает сервер при создании (рекомендуется UUID v4) |
| `name` | string | название проекта; после обрезки пробелов по краям — от 1 до 100 символов |
| `version` | integer ≥ 1 | версия для оптимистичной блокировки: новая сущность — `1`, каждое успешное сохранение — `+1` |
| `createdAt` | string, ISO-8601 UTC | когда создана, например `"2026-10-06T12:04:31.123Z"`; ставит сервер, не меняется |
| `updatedAt` | string, ISO-8601 UTC | когда последний раз сохранена; ставит сервер при каждом сохранении |

**Пример ответа**

```json

  "id": "5b9d54d2-f918-41b5-beff-efc546bf5f0b",
  "name": "Магазин 2.0",
  "version": 4,
  "createdAt": "2026-10-01T09:00:00.000Z",
```

**Поведение**

- Сервер атомарно сравнивает `If-Match` с текущей `version`. Если совпало — сохраняет с `version + 1` и ставит `updatedAt` = время сохранения. Если нет — `409`, ничего не меняется.

### get_spaces

**Список зарисовок проекта.** Вызывает: `ListSpaces` — страница проекта.

```http
GET /projects/{projectId}/spaces?limit=100 HTTP/1.1
Accept: application/json
```

Следующие страницы: `GET /projects/{projectId}/spaces?limit=100&cursor=<nextCursor>`.

**Параметры запроса (query)**

| Параметр | Тип | Обязателен | По умолчанию | Описание |
|---|---|---|---|---|
| `limit` | integer 1…200 | нет | `100` | сколько элементов на страницу; больше 200 — сервер урезает до 200 |
| `cursor` | string | нет | — (первая страница) | значение `nextCursor` из предыдущего ответа. Строка непрозрачная: клиент её не разбирает, только передаёт обратно |

**Заголовки запроса**

| Заголовок | Значение | Обязателен | Описание |
|---|---|---|---|
| `Accept` | `application/json` | да | клиент ждёт JSON |

**Payload:** нет.

**Успешный ответ:** `200 OK`.

**Заголовки ответа**

| Заголовок | Значение | Обязателен | Описание |
|---|---|---|---|
| `Content-Type` | `application/json; charset=utf-8` | да | тело ответа — JSON |

**Схема ответа — страница списка**

| Поле | Тип | Описание |
|---|---|---|
| `items` | array of `Space` | элементы этой страницы (может быть пустым) |
| `nextCursor` | string \| null | курсор следующей страницы; `null` — это последняя страница |
| `total` | integer, необязательно | сколько всего элементов в коллекции на момент запроса; клиенту пока не нужно |

**Схема `Space` (элемент `items`)**

| Поле | Тип | Описание |
|---|---|---|
| `schemaVersion` | integer | версия формата тела; сейчас всегда `1`. Клиент отклонит ответ, где число больше известного ему |
| `id` | string | id сущности; назначает сервер при создании (рекомендуется UUID v4) |
| `projectId` | string | id проекта, к которому относится зарисовка; не меняется |
| `name` | string | название зарисовки; после обрезки пробелов по краям — от 1 до 100 символов |
| `version` | integer ≥ 1 | версия для оптимистичной блокировки: новая сущность — `1`, каждое успешное сохранение — `+1` |
| `createdAt` | string, ISO-8601 UTC | когда создана, например `"2026-10-06T12:04:31.123Z"`; ставит сервер, не меняется |
| `updatedAt` | string, ISO-8601 UTC | когда последний раз сохранена; ставит сервер при каждом сохранении |

**Пример ответа**

```json
{
  "items": [
    {
      "schemaVersion": 1,
      "id": "2bb382d4-fc00-432e-832a-d3935a8f302b",
      "projectId": "5b9d54d2-f918-41b5-beff-efc546bf5f0b",
      "name": "Оплата",
      "version": 2,
      "createdAt": "2026-10-06T12:04:00.000Z",
      "updatedAt": "2026-10-06T12:20:00.000Z"
    }
  ],
  "nextCursor": "eyJjIjoiMjAyNi0xMC0wNlQxMjowNDowMC4wMDBaIiwiaSI6IjJiYjM4MmQ0LWZjMDAtNDMyZS04MzJhLWQzOTM1YThmMzAyYiJ9",
  "total": 4
}
```

На последней странице `"nextCursor": null`. Если зарисовок нет **или проекта с таким id нет** — тоже `200` с `{ "items": [], "nextCursor": null }`, не `404`.

**Поведение**

- Клиент запрашивает страницы, пока `nextCursor` не станет `null`, затем склеивает `items` и убирает дубли по `id`.
- Порядок выдачи: `createdAt` по возрастанию, при равных — `id` по возрастанию. Эти поля у записи не меняются, поэтому при листании ничего не пропадает и не задваивается, а новые записи попадают в конец. Для показа клиент сортирует сам, по `updatedAt`.
- Пока данных мало, можно всегда отдавать всё одной страницей с `"nextCursor": null`.

**Как устроен курсор**

Курсор — закладка «последним на прошлой странице был вот этот элемент». Клиент его не разбирает и не собирает: берёт `nextCursor` из ответа и возвращает как есть в параметре `cursor`, URL-кодированным.

Рекомендуемый формат — JSON с двумя полями последнего элемента страницы, закодированный в **base64url без `=` на конце** (RFC 4648, §5). Такую строку можно вставить в URL без экранирования.

| Поле | Значение |
|---|---|
| `c` | `createdAt` последнего элемента страницы, строка ISO-8601 — **с той же точностью, с какой время хранится в базе** |
| `i` | `id` последнего элемента страницы |

Пример: курсор `eyJjIjoiMjAyNi0xMC0wNlQxMjowNDowMC4wMDBaIiwiaSI6IjJiYjM4MmQ0LWZjMDAtNDMyZS04MzJhLWQzOTM1YThmMzAyYiJ9` раскодируется в

```json
{"c":"2026-10-06T12:04:00.000Z","i":"2bb382d4-fc00-432e-832a-d3935a8f302b"}
```

Как сервер обрабатывает запрос:

1. `limit`: нет — `100`; больше `200` — `200`; меньше `1` или не число — `400 INVALID_DATA`.
2. `cursor`: нет — выдача с начала. Есть — раскодировать base64url, разобрать JSON, проверить, что `c` — дата, а `i` — строка. Не получилось — `400 INVALID_CURSOR`.
3. Выбрать на одну запись больше, чем `limit`. Лишняя запись нужна, только чтобы узнать, есть ли продолжение:

   ```sql
   SELECT * FROM spaces
   WHERE project_id = :projectId
     AND (created_at, id) > (:c, :i)   -- только если пришёл cursor
   ORDER BY created_at, id
   LIMIT :limit + 1
   ```

   Если база не умеет сравнивать пары, то же условие записывается так: `created_at > :c OR (created_at = :c AND id > :i)`. Нужен индекс по `(project_id, created_at, id)`.
4. Пришло больше `limit` записей — лишнюю отбросить, а `nextCursor` собрать из **последней оставшейся** записи. Пришло `limit` или меньше — `nextCursor: null`.
5. `total`, если отдаёте: `SELECT count(*) FROM spaces WHERE project_id = :projectId`.

Тонкости:
- Курсор хранит значения, а не ссылку на запись. Если эту запись потом удалили, курсор продолжает работать: условие «после такого-то времени и id» по-прежнему однозначно.
- Точность времени в курсоре должна совпадать с точностью в базе. Если база хранит микросекунды, а в курсор попадут миллисекунды, записи на границе страниц задвоятся или потеряются. Либо кладите в `c` время с полной точностью, либо округляйте `created_at` до миллисекунд уже при записи.
- Формат курсора — внутреннее дело сервера, его можно поменять в любой момент: клиент на содержимое не смотрит. Подписывать или шифровать курсор не обязательно. Подделанный курсор только сдвинет выдачу, а мусор сервер отклонит с `400 INVALID_CURSOR`.

**Ошибки**

Тело ошибки — объект `error`: `code` (код из таблицы), `message` (описание для логов), а для `404` ещё `entity` и `id` — какой сущности не нашлось. Пример:

```json

```

Заголовок ответа с ошибкой — `Content-Type: application/json; charset=utf-8`.

| Статус | `code` | Когда | Что делает фронтенд |
|---|---|---|---|
| `400` | `INVALID_CURSOR` | `cursor` не удаётся разобрать (не base64url, не JSON, нет полей `c` и `i`) | один раз начинает листание заново с первой страницы |
| `5xx`, сеть, таймаут | — | сбой сервера | показывает «хранилище недоступно» и предлагает повторить |

## Доски

### get_boards

**Список досок зарисовки.** Вызывает: `ListBoards` — боковая панель и обзор зарисовки.

```http
GET /spaces/{spaceId}/boards?limit=100 HTTP/1.1
Accept: application/json
```

Следующие страницы: `GET /spaces/{spaceId}/boards?limit=100&cursor=<nextCursor>`.

**Параметры запроса (query)**

| Параметр | Тип | Обязателен | По умолчанию | Описание |
|---|---|---|---|---|
| `limit` | integer 1…200 | нет | `100` | сколько элементов на страницу; больше 200 — сервер урезает до 200 |
| `cursor` | string | нет | — (первая страница) | значение `nextCursor` из предыдущего ответа. Строка непрозрачная: клиент её не разбирает, только передаёт обратно |

**Заголовки запроса**

| Заголовок | Значение | Обязателен | Описание |
|---|---|---|---|
| `Accept` | `application/json` | да | клиент ждёт JSON |

**Payload:** нет.

**Успешный ответ:** `200 OK`.

**Заголовки ответа**

| Заголовок | Значение | Обязателен | Описание |
|---|---|---|---|
| `Content-Type` | `application/json; charset=utf-8` | да | тело ответа — JSON |

**Схема ответа — страница списка**

| Поле | Тип | Описание |
|---|---|---|
| `items` | array of `BoardSummary` | элементы этой страницы (может быть пустым) |
| `nextCursor` | string \| null | курсор следующей страницы; `null` — это последняя страница |
| `total` | integer, необязательно | сколько всего элементов в коллекции на момент запроса; клиенту пока не нужно |

**Схема `BoardSummary` (элемент `items`) — доска **без `elements`****

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | id сущности; назначает сервер при создании (рекомендуется UUID v4) |
| `spaceId` | string | id зарисовки, к которой относится доска; не меняется |
| `name` | string | название доски; после обрезки пробелов по краям — от 1 до 100 символов |
| `version` | integer ≥ 1 | версия для оптимистичной блокировки: новая сущность — `1`, каждое успешное сохранение — `+1` |
| `createdAt` | string, ISO-8601 UTC | когда создана, например `"2026-10-06T12:04:31.123Z"`; ставит сервер, не меняется |
| `updatedAt` | string, ISO-8601 UTC | когда последний раз сохранена; ставит сервер при каждом сохранении |

**Пример ответа**

```json
{
  "items": [
    {
      "id": "1ca2e07f-7224-40e4-8991-0aea90774e61",
      "spaceId": "2bb382d4-fc00-432e-832a-d3935a8f302b",
      "name": "Схема оплаты",
      "version": 12,
      "createdAt": "2026-10-06T12:05:00.000Z",
      "updatedAt": "2026-10-06T13:40:12.004Z"
    }
  ],
  "nextCursor": "eyJjIjoiMjAyNi0xMC0wNlQxMjowNTowMC4wMDBaIiwiaSI6IjFjYTJlMDdmLTcyMjQtNDBlNC04OTkxLTBhZWE5MDc3NGU2MSJ9",
  "total": 137
}
```

На последней странице `"nextCursor": null`. Если досок нет **или зарисовки с таким id нет** — `200` с `{ "items": [], "nextCursor": null }`, не `404`.

**Поведение**

- Клиент запрашивает страницы, пока `nextCursor` не станет `null`, затем склеивает `items` и убирает дубли по `id`.
- Порядок выдачи: `createdAt` по возрастанию, при равных — `id` по возрастанию. Эти поля у записи не меняются, поэтому при листании ничего не пропадает и не задваивается, а новые записи попадают в конец. Для показа клиент сортирует сам, по `updatedAt`.
- Пока данных мало, можно всегда отдавать всё одной страницей с `"nextCursor": null`.

**Как устроен курсор**

Курсор — закладка «последним на прошлой странице был вот этот элемент». Клиент его не разбирает и не собирает: берёт `nextCursor` из ответа и возвращает как есть в параметре `cursor`, URL-кодированным.

Рекомендуемый формат — JSON с двумя полями последнего элемента страницы, закодированный в **base64url без `=` на конце** (RFC 4648, §5). Такую строку можно вставить в URL без экранирования.

| Поле | Значение |
|---|---|
| `c` | `createdAt` последнего элемента страницы, строка ISO-8601 — **с той же точностью, с какой время хранится в базе** |
| `i` | `id` последнего элемента страницы |

Пример: курсор `eyJjIjoiMjAyNi0xMC0wNlQxMjowNTowMC4wMDBaIiwiaSI6IjFjYTJlMDdmLTcyMjQtNDBlNC04OTkxLTBhZWE5MDc3NGU2MSJ9` раскодируется в

```json
{"c":"2026-10-06T12:05:00.000Z","i":"1ca2e07f-7224-40e4-8991-0aea90774e61"}
```

Как сервер обрабатывает запрос:

1. `limit`: нет — `100`; больше `200` — `200`; меньше `1` или не число — `400 INVALID_DATA`.
2. `cursor`: нет — выдача с начала. Есть — раскодировать base64url, разобрать JSON, проверить, что `c` — дата, а `i` — строка. Не получилось — `400 INVALID_CURSOR`.
3. Выбрать на одну запись больше, чем `limit`. Лишняя запись нужна, только чтобы узнать, есть ли продолжение:

   ```sql
   SELECT * FROM boards
   WHERE space_id = :spaceId
     AND (created_at, id) > (:c, :i)   -- только если пришёл cursor
   ORDER BY created_at, id
   LIMIT :limit + 1
   ```

   Если база не умеет сравнивать пары, то же условие записывается так: `created_at > :c OR (created_at = :c AND id > :i)`. Нужен индекс по `(space_id, created_at, id)`.
4. Пришло больше `limit` записей — лишнюю отбросить, а `nextCursor` собрать из **последней оставшейся** записи. Пришло `limit` или меньше — `nextCursor: null`.
5. `total`, если отдаёте: `SELECT count(*) FROM boards WHERE space_id = :spaceId`.

Тонкости:
- Курсор хранит значения, а не ссылку на запись. Если эту запись потом удалили, курсор продолжает работать: условие «после такого-то времени и id» по-прежнему однозначно.
- Точность времени в курсоре должна совпадать с точностью в базе. Если база хранит микросекунды, а в курсор попадут миллисекунды, записи на границе страниц задвоятся или потеряются. Либо кладите в `c` время с полной точностью, либо округляйте `created_at` до миллисекунд уже при записи.
- Формат курсора — внутреннее дело сервера, его можно поменять в любой момент: клиент на содержимое не смотрит. Подписывать или шифровать курсор не обязательно. Подделанный курсор только сдвинет выдачу, а мусор сервер отклонит с `400 INVALID_CURSOR`.

**Ошибки**

Тело ошибки — объект `error`: `code` (код из таблицы), `message` (описание для логов), а для `404` ещё `entity` и `id` — какой сущности не нашлось. Пример:

```json
{ "error": { "code": "INVALID_CURSOR", "message": "cursor cannot be parsed" } }
```

Заголовок ответа с ошибкой — `Content-Type: application/json; charset=utf-8`.

| Статус | `code` | Когда | Что делает фронтенд |
|---|---|---|---|
| `400` | `INVALID_CURSOR` | `cursor` не удаётся разобрать (не base64url, не JSON, нет полей `c` и `i`) | один раз начинает листание заново с первой страницы |
| `5xx`, сеть, таймаут | — | сбой сервера | показывает «хранилище недоступно» и предлагает повторить |

**Схема `Element` (элемент доски)**

Сервер может не разбирать элементы и хранить массив как есть (например, в `jsonb`). Минимально стоит проверять, что каждый элемент — объект со строковыми `id` и `type`. Неизвестные поля нужно **сохранять как есть**. Id элементов генерирует клиент, они уникальны в пределах доски.

Общие поля всех элементов:

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | id элемента |
| `type` | `"rectangle"` \| `"ellipse"` \| `"diamond"` \| `"line"` \| `"arrow"` \| `"freedraw"` \| `"text"` \| `"document"` \| `"tech"` | тип элемента |
| `x`, `y` | number | левый верхний угол рамки, в координатах доски |
| `width`, `height` | number ≥ 0 | размер рамки |
| `seed` | number | зерно «рукописного» рисунка, чтобы линии не дрожали между перерисовками |
| `style` | object | стиль, поля ниже |

Поля `style`:

| Поле | Тип | Описание |
|---|---|---|
| `strokeColor` | string | цвет линий, CSS-цвет, например `"#1e1e1e"` |
| `fillColor` | string | цвет заливки, CSS-цвет или `"transparent"` |
| `fillStyle` | `"hachure"` \| `"cross-hatch"` \| `"solid"`, необязательно | тип заливки; нет поля — `"hachure"` |
| `strokeWidth` | number | толщина линий |
| `roughness` | number | небрежность линий: `0` ровно, `1` небрежно, `2` очень небрежно |

Дополнительные поля по типам. Поля с пометкой «необязательно» могут отсутствовать в старых данных, тогда клиент подставляет значение по умолчанию.

| `type` | Поле | Тип | Описание |
|---|---|---|---|
| `rectangle`, `ellipse`, `diamond` | `label` | string, необязательно | подпись внутри фигуры; нет поля — `""` |
| `tech` | `kind` | `"service"` \| `"database"` \| `"cache"` \| `"queue"` \| `"storage"` \| `"function"` \| `"server"` \| `"gateway"` \| `"loadBalancer"` \| `"external"` \| `"web"` \| `"mobile"` \| `"user"` | вид ИТ-компонента |
| `tech` | `label` | string, необязательно | подпись; нет поля — `""` |
| `line`, `arrow` | `points` | array of `{ "x": number, "y": number }` | точки относительно `x, y`: первая и последняя — концы, между ними — точки изгиба |
| `line`, `arrow` | `curved` | boolean, необязательно | `true` — плавная кривая через точки, `false` — ломаная; нет поля — `false` |

- Сервер атомарно сравнивает `If-Match` с текущей `version`. Если совпало — сохраняет с `version + 1` и ставит `updatedAt` = время сохранения. Если нет — `409`, ничего не меняется.

- Порядок `elements` — порядок слоёв, его нужно сохранить точно.

| `422` | `INVALID_NAME` | название пустое или длиннее 100 символов после обрезки пробелов | показывает ошибку названия |

| `5xx`, сеть, таймаут | — | сбой сервера | показывает «хранилище недоступно» и предлагает повторить |

## Документы

### get_documents

**Список документов зарисовки.** Вызывает: `ListDocuments` — боковая панель, обзор зарисовки и меню «Документ» на доске.

```http
GET /spaces/{spaceId}/documents?limit=100 HTTP/1.1
Accept: application/json
```

Следующие страницы: `GET /spaces/{spaceId}/documents?limit=100&cursor=<nextCursor>`.

**Параметры запроса (query)**

| Параметр | Тип | Обязателен | По умолчанию | Описание |
|---|---|---|---|---|
| `limit` | integer 1…200 | нет | `100` | сколько элементов на страницу; больше 200 — сервер урезает до 200 |
| `cursor` | string | нет | — (первая страница) | значение `nextCursor` из предыдущего ответа. Строка непрозрачная: клиент её не разбирает, только передаёт обратно |

**Заголовки запроса**

| Заголовок | Значение | Обязателен | Описание |
|---|---|---|---|
| `Accept` | `application/json` | да | клиент ждёт JSON |

**Payload:** нет.

**Успешный ответ:** `200 OK`.

**Заголовки ответа**

| Заголовок | Значение | Обязателен | Описание |
|---|---|---|---|
| `Content-Type` | `application/json; charset=utf-8` | да | тело ответа — JSON |

**Схема ответа — страница списка**

| Поле | Тип | Описание |
|---|---|---|
| `items` | array of `DocumentSummary` | элементы этой страницы (может быть пустым) |
| `nextCursor` | string \| null | курсор следующей страницы; `null` — это последняя страница |
| `total` | integer, необязательно | сколько всего элементов в коллекции на момент запроса; клиенту пока не нужно |

**Схема `DocumentSummary` (элемент `items`) — документ **без `content`****

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | id сущности; назначает сервер при создании (рекомендуется UUID v4) |
| `spaceId` | string | id зарисовки, к которой относится документ; не меняется |
| `title` | string | заголовок документа; после обрезки пробелов по краям — от 1 до 100 символов |
| `version` | integer ≥ 1 | версия для оптимистичной блокировки: новая сущность — `1`, каждое успешное сохранение — `+1` |
| `createdAt` | string, ISO-8601 UTC | когда создана, например `"2026-10-06T12:04:31.123Z"`; ставит сервер, не меняется |
| `updatedAt` | string, ISO-8601 UTC | когда последний раз сохранена; ставит сервер при каждом сохранении |

**Пример ответа**

```json
{
  "items": [
    {
      "id": "9550969e-9116-4e70-b777-822713345ceb",
      "spaceId": "2bb382d4-fc00-432e-832a-d3935a8f302b",
      "title": "Платёжный API",
      "version": 5,
      "createdAt": "2026-10-06T12:06:00.000Z",
      "updatedAt": "2026-10-06T12:30:00.000Z"
    }
  ],
  "nextCursor": "eyJjIjoiMjAyNi0xMC0wNlQxMjowNjowMC4wMDBaIiwiaSI6Ijk1NTA5NjllLTkxMTYtNGU3MC1iNzc3LTgyMjcxMzM0NWNlYiJ9",
  "total": 23
}
```

На последней странице `"nextCursor": null`. Если документов нет **или зарисовки с таким id нет** — `200` с `{ "items": [], "nextCursor": null }`, не `404`.

**Поведение**

- Клиент запрашивает страницы, пока `nextCursor` не станет `null`, затем склеивает `items` и убирает дубли по `id`.
- Порядок выдачи: `createdAt` по возрастанию, при равных — `id` по возрастанию. Эти поля у записи не меняются, поэтому при листании ничего не пропадает и не задваивается, а новые записи попадают в конец. Для показа клиент сортирует сам, по `updatedAt`.
- Пока данных мало, можно всегда отдавать всё одной страницей с `"nextCursor": null`.

**Как устроен курсор**

Курсор — закладка «последним на прошлой странице был вот этот элемент». Клиент его не разбирает и не собирает: берёт `nextCursor` из ответа и возвращает как есть в параметре `cursor`, URL-кодированным.

Рекомендуемый формат — JSON с двумя полями последнего элемента страницы, закодированный в **base64url без `=` на конце** (RFC 4648, §5). Такую строку можно вставить в URL без экранирования.

| Поле | Значение |
|---|---|
| `c` | `createdAt` последнего элемента страницы, строка ISO-8601 — **с той же точностью, с какой время хранится в базе** |
| `i` | `id` последнего элемента страницы |

Пример: курсор `eyJjIjoiMjAyNi0xMC0wNlQxMjowNjowMC4wMDBaIiwiaSI6Ijk1NTA5NjllLTkxMTYtNGU3MC1iNzc3LTgyMjcxMzM0NWNlYiJ9` раскодируется в

```json
{"c":"2026-10-06T12:06:00.000Z","i":"9550969e-9116-4e70-b777-822713345ceb"}
```

Как сервер обрабатывает запрос:

1. `limit`: нет — `100`; больше `200` — `200`; меньше `1` или не число — `400 INVALID_DATA`.
2. `cursor`: нет — выдача с начала. Есть — раскодировать base64url, разобрать JSON, проверить, что `c` — дата, а `i` — строка. Не получилось — `400 INVALID_CURSOR`.
3. Выбрать на одну запись больше, чем `limit`. Лишняя запись нужна, только чтобы узнать, есть ли продолжение:

   ```sql
   SELECT * FROM documents
   WHERE space_id = :spaceId
     AND (created_at, id) > (:c, :i)   -- только если пришёл cursor
   ORDER BY created_at, id
   LIMIT :limit + 1
   ```

   Если база не умеет сравнивать пары, то же условие записывается так: `created_at > :c OR (created_at = :c AND id > :i)`. Нужен индекс по `(space_id, created_at, id)`.
4. Пришло больше `limit` записей — лишнюю отбросить, а `nextCursor` собрать из **последней оставшейся** записи. Пришло `limit` или меньше — `nextCursor: null`.
5. `total`, если отдаёте: `SELECT count(*) FROM documents WHERE space_id = :spaceId`.

Тонкости:
- Курсор хранит значения, а не ссылку на запись. Если эту запись потом удалили, курсор продолжает работать: условие «после такого-то времени и id» по-прежнему однозначно.
- Точность времени в курсоре должна совпадать с точностью в базе. Если база хранит микросекунды, а в курсор попадут миллисекунды, записи на границе страниц задвоятся или потеряются. Либо кладите в `c` время с полной точностью, либо округляйте `created_at` до миллисекунд уже при записи.
- Формат курсора — внутреннее дело сервера, его можно поменять в любой момент: клиент на содержимое не смотрит. Подписывать или шифровать курсор не обязательно. Подделанный курсор только сдвинет выдачу, а мусор сервер отклонит с `400 INVALID_CURSOR`.

**Ошибки**

Тело ошибки — объект `error`: `code` (код из таблицы), `message` (описание для логов), а для `404` ещё `entity` и `id` — какой сущности не нашлось. Пример:

```json
{ "error": { "code": "INVALID_CURSOR", "message": "cursor cannot be parsed" } }
```

Заголовок ответа с ошибкой — `Content-Type: application/json; charset=utf-8`.

| Статус | `code` | Когда | Что делает фронтенд |
|---|---|---|---|
| `400` | `INVALID_CURSOR` | `cursor` не удаётся разобрать (не base64url, не JSON, нет полей `c` и `i`) | один раз начинает листание заново с первой страницы |
| `5xx`, сеть, таймаут | — | сбой сервера | показывает «хранилище недоступно» и предлагает повторить |

| `marks` | array of `{ "type": string, "attrs"?: object }`, необязательно | оформление текста (только у узлов `text`) |
| `text` | string, необязательно | сам текст (только у узлов `text`) |

- **узлы:** `doc`, `paragraph`, `heading` (`attrs.level`: 1–6), `text`, `bulletList`, `orderedList`, `listItem`, `taskList`, `taskItem` (`attrs.checked`: boolean), `blockquote`, `codeBlock` (`attrs.language`: строка или `null`), `horizontalRule`, `hardBreak`;
